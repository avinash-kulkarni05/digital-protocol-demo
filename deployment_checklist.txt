====================================================================
  DEPLOYMENT CHECKLIST — Clinical Trial Protocol Digitalization Platform
  Last Updated: February 15, 2026
====================================================================

Use this checklist before every publish to avoid common deployment failures.


--------------------------------------------------------------------
1. DEPLOYMENT TARGET: Must be "VM" (not "Autoscale")
--------------------------------------------------------------------
PROBLEM:  This app runs two processes (Python backend on port 8080 +
          Node.js frontend on port 5000). Autoscale has a strict
          startup timeout and will fail because both processes take
          too long to initialize.

FIX:      Set deployment target to "vm" in the deployment config.
          VM keeps the app running continuously and gives it enough
          time to start both processes.

BUILD CMD: bash -c "cd backend_vNext && pip install -r requirements.txt && cd ../frontend-vNext && npm install && npx tsx script/build.ts"

RUN CMD:  bash -c "cd backend_vNext && python3 run.py --host 0.0.0.0 --port 8080 2>&1 & sleep 3 && cd frontend-vNext && NODE_ENV=production node dist/index.cjs"


--------------------------------------------------------------------
2. ROOT package.json REQUIRED
--------------------------------------------------------------------
PROBLEM:  Replit runs "npm install" and "npm run build" from the
          workspace root. Without a root package.json, it can't
          find the frontend dependencies or build script.

FIX:      A root-level package.json must exist with these scripts:
            - "postinstall": "cd frontend-vNext && npm install"
            - "build": "cd frontend-vNext && npm run build"
            - "start": "cd frontend-vNext && npm run start"


--------------------------------------------------------------------
3. REBUILD PRODUCTION BUNDLE BEFORE PUBLISHING
--------------------------------------------------------------------
PROBLEM:  The production bundle (frontend-vNext/dist/index.cjs) can
          become stale if source code changes but the bundle isn't
          rebuilt. This causes "Cannot find module" errors for
          libraries that were removed from the code but still
          referenced in the old bundle.

EXAMPLE:  "http-proxy-middleware" was removed from server code but
          the old dist/index.cjs still required it, causing a crash.

FIX:      Always rebuild before publishing:
            cd frontend-vNext && npx tsx script/build.ts

VERIFY:   Test the production build locally:
            cd frontend-vNext && NODE_ENV=production node dist/index.cjs
          (It should start without module errors. An EADDRINUSE error
          is OK — it just means the dev server is already using the port.)


--------------------------------------------------------------------
4. NO import.meta.url IN BUNDLED SERVER CODE
--------------------------------------------------------------------
PROBLEM:  The esbuild config outputs CommonJS format (dist/index.cjs).
          "import.meta.url" is an ES Module feature and returns
          undefined in CJS, causing a crash:
            TypeError: The "path" argument must be of type string

WHERE:    This was in server/db.ts, used to resolve the .env file path.

FIX:      Use process.cwd() instead of import.meta.url for resolving
          file paths in any server-side code:
            BEFORE: const __filename = fileURLToPath(import.meta.url);
                    dotenv.config({ path: path.resolve(__dirname, "../../.env") });
            AFTER:  dotenv.config({ path: path.resolve(process.cwd(), "../.env") });


--------------------------------------------------------------------
5. ESBUILD ALLOWLIST vs EXTERNALS
--------------------------------------------------------------------
PROBLEM:  The build script (frontend-vNext/script/build.ts) bundles
          only dependencies listed in the "allowlist" array. Everything
          else is marked as "external" — meaning it must be available
          in node_modules at runtime.

          If a dependency is external but not installed, the production
          build will crash with "Cannot find module".

FIX:      When adding a new server-side dependency:
            Option A: Add it to the allowlist in script/build.ts
                      (it gets bundled into dist/index.cjs)
            Option B: Make sure it's in package.json "dependencies"
                      (it stays external but gets installed)

          When removing a dependency from server code:
            - Always rebuild dist/index.cjs so the old reference is gone.


--------------------------------------------------------------------
6. DATABASE SCHEMA — Use "public" Schema Only
--------------------------------------------------------------------
PROBLEM:  Both backend (SQLAlchemy) and frontend (Drizzle ORM) access
          the same PostgreSQL database. All tables must be in the
          "public" schema to avoid "relation does not exist" errors.

FIX:      - Backend: SQLAlchemy models use __table_args__ = {"schema": "public"}
          - Frontend: Drizzle schema uses { schema: "public" } in table defs
          - Connection pool sets search_path: SET search_path TO public


--------------------------------------------------------------------
7. PDF LOADING — Use ArrayBuffer Pattern
--------------------------------------------------------------------
PROBLEM:  Direct URL-based PDF loading fails in Replit's iframe
          environment because the react-pdf web worker can't fetch
          URLs through the proxy.

FIX:      Fetch PDFs as ArrayBuffer through the frontend proxy, then
          pass { data: new Uint8Array(buffer) } to the react-pdf
          Document component.

          Proxy routes:
            /api/protocols/:studyId/pdf
            /api/protocols/:studyId/pdf/annotated

          These forward to the Python backend which serves the actual PDFs.


--------------------------------------------------------------------
8. NO LOCALHOST REFERENCES IN FRONTEND CODE
--------------------------------------------------------------------
PROBLEM:  The app runs in the cloud. Any "localhost:8080" reference
          in client-side code will fail because the user's browser
          can't reach the server's localhost.

FIX:      All backend API calls from the React frontend must go through
          the Express proxy at /api/backend/* which forwards to the
          Python backend internally.


--------------------------------------------------------------------
9. PYTHON BACKEND DEPENDENCIES MUST BE INSTALLED IN BUILD
--------------------------------------------------------------------
PROBLEM:  The production build step only built the frontend (npm run
          build). Python dependencies were never installed, so the
          backend process crashed immediately with ImportError — but
          because it runs in the background (&), the error was silent
          and the frontend started without a working backend.

          Result: ECONNREFUSED 127.0.0.1:8080 when frontend tries to
          proxy requests to the backend.

FIX:      The deployment BUILD command must install Python deps first:
            cd backend_vNext && pip install -r requirements.txt

          The RUN command should start backend first with a short delay
          so it's ready before the frontend tries to connect:
            cd backend_vNext && python3 run.py ... 2>&1 &
            sleep 3 &&
            cd frontend-vNext && NODE_ENV=production node dist/index.cjs

          The "2>&1" ensures any backend errors appear in the production
          logs instead of being silently lost.


--------------------------------------------------------------------
10. BACKEND STARTUP RACE CONDITION (ECONNREFUSED on Deploy)
--------------------------------------------------------------------
PROBLEM:  On production startup, the frontend (Express on port 5000)
          starts before the Python backend (port 8080) is ready. Any
          request that arrives during this window gets proxied to the
          backend and fails with:
            Backend proxy error: TypeError: fetch failed
            [cause]: Error: connect ECONNREFUSED 127.0.0.1:8080

          This is a transient error that resolves once the backend
          finishes starting (usually a few seconds), but it creates
          noisy error logs and may cause the first user request to fail.

FIX:      Added a fetchWithRetry() helper in server/routes.ts that
          wraps all backend proxy calls. When a connection is refused,
          it retries up to 3 times with a 2-second delay between attempts.
          This silently absorbs the startup gap.

FILE:     frontend-vNext/server/routes.ts — fetchWithRetry() function

NOTE:     The RUN command also uses "sleep 3" before starting the
          frontend, but this alone is not always sufficient on slower
          cold starts.


--------------------------------------------------------------------
11. STUCK "PROCESSING" PROTOCOLS (Failed Worker Process)
--------------------------------------------------------------------
PROBLEM:  If the production server restarts or redeploys while an
          extraction is running, the worker process gets killed. The
          job record is updated to "failed" but the protocol's
          extraction_status remains stuck at "processing". The
          dashboard shows "Processing... 0%" permanently with no way
          to retry.

          Example: NCT03003962_Protocol was stuck in "processing"
          after a deployment killed its extraction worker.

FIX:      Two changes were made:

          1. Backend reset endpoint:
             POST /api/v1/protocols/{protocol_id}/reset-status
             Resets a stuck protocol's extraction_status from
             "processing" back to "uploaded" so extraction can be
             retried. Returns 400 if the protocol is already completed.

          2. Frontend stuck detection (LandingPage.tsx):
             When the dashboard loads, protocols with status "processing"
             are checked against their latest job. If the latest job is
             "failed" or "completed" (not actively running), the card
             switches from "Processing... 0%" to "Failed — Retry
             Extraction". Clicking retry automatically calls the
             reset endpoint and then starts a new extraction.

FILES:    backend_vNext/app/routers/protocol.py — reset-status endpoint
          frontend-vNext/client/src/lib/api.ts — resetProtocolStatus()
          frontend-vNext/client/src/pages/LandingPage.tsx — stuck detection

12. LOGIN PAGE & SESSION AUTHENTICATION
--------------------------------------------------------------------
ADDED:    A session-based login system that restricts access to
          authorized Saama personnel only.

REQUIREMENTS:
  - Only @saama.com email addresses are accepted
  - Password must match the APP_PASSWORD Replit secret
  - The APP_PASSWORD secret MUST be set before deploying

HOW IT WORKS:
  - Express-session middleware with connect-pg-simple stores sessions
    in PostgreSQL (auto-creates a "session" table)
  - Sessions last 7 days before requiring re-login
  - All data API routes (/api/protocols, /api/documents, /api/backend)
    are protected by requireAuth middleware
  - Auth endpoints:
      POST /api/auth/login   — validates email + password, creates session
      POST /api/auth/logout  — destroys session
      GET  /api/auth/check   — returns current auth status

FRONTEND:
  - AuthProvider context (client/src/lib/auth.tsx) manages login state
  - LoginPage component (client/src/pages/LoginPage.tsx) with Saama
    branding is shown before any app content
  - Header shows logged-in user's name and a "Sign Out" button

SECURITY:
  - Session secret uses APP_PASSWORD (falls back to a random
    cryptographic key if not set, but login will fail without it)
  - Cookies are httpOnly and secure in production (NODE_ENV=production)
  - Trust proxy is enabled in production for correct cookie behavior
    behind Replit's reverse proxy

FILES:    frontend-vNext/server/index.ts — session middleware, trust proxy
          frontend-vNext/server/routes.ts — auth endpoints, requireAuth
          frontend-vNext/client/src/lib/auth.tsx — AuthProvider context
          frontend-vNext/client/src/pages/LoginPage.tsx — login UI
          frontend-vNext/client/src/components/layout/Header.tsx — user info + sign out

SECRET:   APP_PASSWORD must be set in Replit Secrets before deploying.
          Without it, no one can log in.


--------------------------------------------------------------------
13. AUTO-REPAIR DATABASE SCHEMA ON STARTUP
--------------------------------------------------------------------
PROBLEM:  Some tables (usdm_documents, usdm_edit_audit, soa_edit_audit,
          job_events) were created without auto-increment sequences on
          their primary key columns. This caused INSERT failures after
          redeployment.

FIX:      A repairSchema() function runs automatically when the
          frontend server starts. It checks for missing sequences and
          constraints and creates them if needed. This is idempotent
          and safe to run on every startup.

FILE:     frontend-vNext/server/db.ts — repairSchema()

--------------------------------------------------------------------

  [ ] 2. Confirm Python backend dependencies are installed:
         cd backend_vNext && pip install -r requirements.txt

  [ ] 3. Test Python backend starts:
         cd backend_vNext && python3 run.py --host 0.0.0.0 --port 8080

  [ ] 4. Rebuild production bundle:
         cd frontend-vNext && npx tsx script/build.ts

  [ ] 5. Test production server starts (expect EADDRINUSE if dev is running):
         cd frontend-vNext && NODE_ENV=production node dist/index.cjs

  [ ] 6. Confirm no "Cannot find module" errors in step 5

  [ ] 7. Confirm deployment target is set to "vm"

  [ ] 8. Confirm deployment BUILD installs Python deps:
         bash -c "cd backend_vNext && pip install -r requirements.txt && ..."

  [ ] 9. Confirm root package.json exists with postinstall and build scripts

  [ ] 10. Confirm both workflows run without errors:
          - Python Backend (port 8080)
          - Start application (port 5000)

  [ ] 11. Test login flow in the browser preview:
          - Login page appears on first visit
          - Non-@saama.com emails are rejected
          - Correct password logs in successfully
          - Header shows user name and Sign Out button
          - Sign Out returns to login page

  [ ] 12. Test the app in the browser preview — check PDF loading,
          document list, and review pages

  [ ] 13. Check for any stuck "Processing" protocols on the dashboard
          (they should now show "Failed — Retry Extraction")

  [ ] 14. Click Publish
